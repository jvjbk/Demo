# 出库拣选「到位缺货」根因分析与前置标记

> 数据：`pick_tasks.csv`（1292 行，2026-09-01 ~ 2026-09-07 共 7 天）
> 口径：每次到位缺货损失 90 分钟；每次提前标记缺货花费 12 分钟

---

## 0. 一句话结论

**缺货不是"库存不准"造成的，是"库存快照有两条同步链路"造成的。**
21% 的任务在派发时用了一份滞后 22~70 分钟的库存快照，
这批任务的缺货率 27.8%，是正常链路（3.9%）的 7.2 倍，制造了全部缺货的 65.7%。

派发前按这条规则做标记，7 天可少空跑 69 次、净省 3234 分钟（53.9 小时）；
而把这条慢链路修好，可再省 5336 分钟（88.9 小时），且没有反复成本。

---

## 1. 我的判断

### 1.1 先看到的三个数据事实（不先处理，后面全是错的）

**事实一：1292 行里有 62 行是完全重复的整行。**

按 `task_id` 去重只有 1230 个，正好少 62 个，说明是同一批任务被重复上报了两次。
如果不去重，缺货率会从 8.91% 被算成 8.89%，波次统计也会重复计数。
**处理：按整行签名去重，后续一律用 1230 个唯一任务。**

**事实二：两个时间字段的时区不一样。**

`pick_time` 是 `+08:00`（北京时间），`stock_synced_at` 是 `Z`（UTC）。
直接把两个字符串相减，每条任务都会恒定多出 **480 分钟**的滞后。
这不是小误差——它会把"滞后 11 分钟"算成"滞后 491 分钟"，
让所有任务看起来都严重过期，整个归因方向就反了。
**处理：各自解析出时区后统一换算到 UTC 再相减。**

**事实三：55 行（去重后 51 行）`is_success` 是空的，占 4.1%。**

这是作业未回传或异常中断，不是"没缺货"。
**处理：算缺货率时从分母里剔除，但不从任务池里丢掉——这些恰恰是最该提前标记的。**

### 1.2 根问题：库存快照是一对双峰，不是连续漂移

把每行任务的"快照滞后"算出来，按分钟列出来，得到这样一个形状：

    滞后 0~18 分钟：931 条，密集分布
    滞后 19、20、21 分钟：一条都没有
    滞后 22~70 分钟：248 条

**中间是空的。**这不是"同步慢慢变慢"，如果是的话，20 分钟附近应该有大量样本。
断档说明系统里存在**两条不同的库存同步路径**：
一条正常（≤18 分钟），一条走了另一个出口，滞后 22~70 分钟。

两条链路的后果差得非常远：

    快链路（滞后 ≤20 分钟）：任务 931 条（占 79.0%），缺货 36 条，缺货率 3.87%
    慢链路（滞后 > 20 分钟）：任务 248 条（占 21.0%），缺货 69 条，缺货率 27.82%

慢链路的缺货率是快链路的 **7.2 倍**。
**只用 21% 的任务量，制造了 65.7% 的缺货。**
所以这是一件"少数任务贡献大部分损失"的事，能精准定位、也能低成本拦住。

### 1.3 为什么不是"波次太大"，也不是"库存太低"

这两个是第一直觉，都经不起数据检验。

**关于波次规模：**表面上看波次越大缺货越多（波次 ≤50 缺货 6.2%，51~82 缺货 10.7%）。
但把滞后固定住之后，这个效应几乎消失了：

    只看快链路：波次 ≤50 缺货 3.40%，波次 51~82 缺货 4.47%   ← 基本持平
    只看慢链路：波次 ≤50 缺货 23.68%，波次 51~82 缺货 28.30% ← 才有梯度

也就是说，波次本身不直接造成缺货。真实的链条是：
**一次发大波次 → 库存同步任务积压 → 快照变旧 → 缺货**。
证据是慢链路占比随波次单调上升：

    波次 ≤25：慢链路占 12.5%
    波次 26~50：慢链路占 14.0%
    波次 51~75：慢链路占 25.4%
    波次 76 以上：慢链路占 40.8%

所以"限制波次大小"只能绕开症状，而且会牺牲出库产能。
该修的是同步链路本身。

**关于账面库存 `avail_stock`：**这个字段看着最像"库存不足"，但它不是物理库存，是**过期快照上的账面数**。
最硬的反证：账面可用库存 = 0 的 36 条任务里，有 28 条（77.8%）最后还是把货拣出来了。
账面无货 ≠ 货位无货。同理，账面有货也不代表货位有货。
所以不能按这个字段排优先级（见下面的判别力检验）。

**三个单因子的判别力对比（AUC，0.5 相当于瞎猜）：**

    lag_min 快照滞后                    AUC = 0.754
    wave_task_count 波次规模            AUC = 0.622
    avail_stock 取负（低库存=高风险）    AUC = 0.547

滞后是唯一有实用判别力的因子；账面库存单用几乎等于瞎猜。
但它不能扔——和滞后叠起来之后，它能把风险再分一层（见 2.2）。

## 2. 做了什么

### 2.1 交付物

    pick_risk.py    主程序：归因报告 + 逐任务风险标记清单（纯标准库，无第三方依赖）
    verify.py       独立复算脚本：用另一套代码重算本文所有关键数字，24 项校验
    out/risk_flags.csv   1230 条任务的标记结果（含 p_miss、建议动作、事后对错）
    out/summary.txt      报告全文快照
    run.bat / run.sh     一键运行

### 2.2 风险模型：只有 4 个格子，能人工核对

没有用机器学习（1179 条标注样本，用复杂模型只会过拟合）。
只用两个因子交叉：**快照是否过期 × 账面库存是否偏低**，得到 4 个分段，
每段用历史缺货率估计风险（Laplace 平滑，向整体基础率收缩，避免小样本给出 0% 或 100%）：

    快照过期 · 账面库存低 ：样本  26 条，缺货 11 条（42.3%），估计 p=0.399
    快照过期 · 账面库存正常：样本 222 条，缺货 58 条（26.1%），估计 p=0.260
    快照新鲜 · 账面库存低 ：样本  94 条，缺货 14 条（14.9%），估计 p=0.148
    快照新鲜 · 账面库存正常：样本 837 条，缺货 22 条（ 2.6%），估计 p=0.026

四个数字，任何人拿计算器都能验。波次规模**故意不放进模型**——
它是上游触发器，放进来会重复计算同一件事。

### 2.3 决策阈值是算出来的，不是拍的

这是整个方案里最反对"凭感觉定 0.5"的地方。
提前标记要花 12 分钟，标记对了省下 90 分钟，标错了白花 12 分钟。
所以只有满足下式才值得标记：

    p × 90 > 12   →   p > 12/90 = 13.33%

**13.33% 就是盈亏平衡点，是算术结论，不是调参调出来的。**

不过实际推荐把阈值抬到 26%，原因见下：

    p ≥ 39.9% 起累加：标记  26 条，命中 11 次，误报 15 次，净省  678 分钟
    p ≥ 26.0% 起累加：标记 248 条，命中 69 次，误报 179 次，净省 3234 分钟   ← 推荐
    p ≥ 14.8% 起累加：标记 342 条，命中 83 次，误报 259 次，净省 3366 分钟
    p ≥  2.6% 起累加：标记 1179 条，命中 105 次，误报 1074 次，净省 -4698 分钟 ← 亏
    一条都不标记    ：标记   0 条，净省 0 分钟

从 26% 降到 14.8% 只多省 132 分钟，却要多打扰一线 94 次。
12 分钟的账面上是"划算"的，但误报对一线信任的杀伤没被这个数字计入。
**所以推荐 26%：只标慢链路，少打扰、几乎不少赚。**
最后一行也说明：无差别全量标记会把收益做成负数。

注：上面 248 条是"已回传且被标记"的数量，为了和历史结果对账用。
实际下发的清单覆盖全部 1230 条任务，其中另有 11 条快照过期的任务尚未回传，
也会被标记，所以 `out/risk_flags.csv` 里被标记的是 259 条。

### 2.4 落地建议（两件事，不要只做第二件）

    第一件（根治）：查清那条滞后 22~70 分钟的同步路径为什么存在——
                    是备用通道、是消息积压、还是某个同步任务超时后降级？
                    修好它，慢链路的 69 次缺货基本可以消掉。
    第二件（兜底）：在修好之前，派发环节加一道前置校验：
                    快照过期 → 挂起派发，先对货位做一次实时库存校验（12 分钟）
                    快照新鲜但账面偏低 → 派发前人工确认余量
                    其余 → 正常下发

两件事的收益**不能相加**。慢链路修好后，规则会自动退化成只抓"快照新鲜+账面低库存"
那一小撮（该格缺货率 14.9%，净收益很薄），到时候可以只保留监控、不做拦截。

## 3. 怎么证明有用

### 3.1 全部由数据算出的关键数字

数据规模与质量：

    CSV 原始 1292 行 → 剔除 62 行重复 → 1230 个唯一任务
    其中已回传 1179 条，未回传 51 条（4.1%，不计入缺货率分母）
    整体缺货 105 / 1179 = 8.91%
    基准损失 105 × 90 = 9450 分钟（7 天，即 157.5 小时）

根因定位：

    快链路 931 条 → 缺货 36 条 → 3.87%
    慢链路 248 条 → 缺货 69 条 → 27.82%
    慢链路缺货率是快链路的 7.2 倍，占总缺货 65.7%
    滞后分布 0~70 分钟，19/20/21 分钟零样本（断层 = 两条链路）
    账面库存 = 0 的 36 条里 28 条（77.8%）仍拣货成功

策略收益（回放 1179 条已回传任务）：

    推荐策略（只标慢链路，阈值 26%）
      标记 248 条，命中 69 次，误报 179 次
      召回率 65.7%（69/105），精确率 27.8%（69/248）
      净省 69×90 - 248×12 = 6210 - 2976 = 3234 分钟 = 53.9 小时
      折合每个自然日 462 分钟 ≈ 7.7 小时
      相当于把 9450 分钟的基准损失砍掉 34.2%

    对比：无差别全量标记
      105×90 - 1179×12 = 9450 - 14148 = -4698 分钟（净亏 78.3 小时）

根治收益（不是估算，是按快链路实测缺货率外推）：

    慢链路 248 条里，账面正常 222 条、账面低 26 条
    按快链路同档缺货率（2.6% / 14.9%）推算，修好后预计只剩 9.7 条缺货
    即每 7 天少 69 - 9.7 = 59.3 次空跑，少损失 5336 分钟 = 88.9 小时

### 3.2 防自我印证：时间外推检验

上面 3234 分钟是全样本回放，有"用历史解释历史"的嫌疑。
所以再切一刀：**前 5 天训练，最后 2 天完全当未来数据，规则不能改。**

    训练 2026-09-01 ~ 09-05：861 条，缺货 75 条，净省 2460 分钟
    检验 2026-09-06 ~ 09-07：318 条，缺货 30 条，净省  906 分钟
    检验集召回 76.7%，精确率 23.7%

后两天没见过的数据上净节省仍为正，说明规则不是靠记住样本。

### 3.3 复现步骤（两条命令，不需要任何第三方包）

环境：Python 3.8 以上即可，不需要 pandas / numpy / scikit-learn。

    cd D:\Users\33539\Desktop\shixun

    # 1) 自检：用独立代码重算本文所有关键数字，应全部 PASS
    python verify.py
    #   期望最后一行：通过 24 项，失败 0 项

    # 2) 完整归因报告 + 生成标记清单
    python pick_risk.py
    #   屏幕上打印本文第 1~3 节的全部数字
    #   同时写出 out/risk_flags.csv 和 out/summary.txt

    # 3) 只标慢链路（推荐上线口径）
    python pick_risk.py flag --only-stale
    #   标记 259 条（其中 248 条已回传、11 条未回传）
    #   若只想按自定义概率阈值，可用 --min-p 0.3 这类明显偏离分段边界的值，
    #   不要照抄报告里四舍五入后的 0.26——真实概率可能略低于它，会漏掉整个分段

Windows 下也可直接双击 `run.bat`，Linux/macOS 用 `bash run.sh`。

`verify.py` 故意不 import 主程序，而是用另一套手工时间戳解析逻辑重算，
如果主程序的时区处理错了，自检会 FAIL 而不是跟着一起错。
它校验的 24 项里包括：原始行数 1292、重复行 62、唯一任务 1230、
滞后范围 0~70、断层值 19/20/21、忽略时区后的恒定偏差 480 分钟、
快链路 931/36、慢链路 248/69、慢链路占比 65.7%、账面为 0 的 36 条中 28 条成功、
只标慢链路净省 3234 分钟、全量标记净省 -4698 分钟。

### 3.4 怎么验证"上线后真的有效"

`out/risk_flags.csv` 每行都带 `outcome` 字段（命中 / 误报 / 漏报 / 正确放行 / 未回传），
上线后把实际回传结果接进去，就能按周直接对账：
**本周标记 N 次，命中 M 次，净省 = M×90 - N×12 分钟。**
如果连续两周净省为负，说明链路已经修好或分布变了，重新跑一次 `pick_risk.py` 重估即可。

## 4. 上线要注意的

**阈值不是永久常数。**26% 是从这 7 天数据来的。业务量、SKU 结构、
同步链路状态一变就要重估。脚本每次跑都会重新估计，不要把它写死在代码里。

**特征只有 4 格，粒度天生粗。**它能把慢链路整体挑出来，但挑不出
"慢链路里哪一单真的没货"。要更细，需要补货位维度的实时库存变动流水，
而不是在这个 CSV 上加特征。

**误报率 72.2% 听起来吓人，但这是算过账的选择。**
179 次误报 × 12 分钟 = 2148 分钟成本，换来 69 次 × 90 分钟 = 6210 分钟的止损，
净赚 3234 分钟。真正的风险不是误报本身，是如果一线因为误报而不信任标记、
开始直接忽略，规则就失效了。**所以第一件事应该是修链路，让规则可以退休。**

**"滞后 > 20 分钟"这条线是从数据断层里读出来的，不是业务规矩。**
它和 19/20/21 分钟零样本正好吻合，但换一批数据就要重新找断点，
不要当成先验写死。

## 5. 这个分析没解决的问题

- **不知道慢链路为什么存在。**数据只能证明有两条路径、
  能定位到滞后 22~70 分钟这个区间，但看不出是哪个服务、哪个任务、
  是超时降级还是消息积压。这需要看同步服务的日志和配置，CSV 里没有。
- **51 条未回传任务的真实结果未知。**占 4.1%，如果它们系统性偏向缺货，
  实际缺货率会高于 8.91%，收益也会更高。
- **没有货位和 SKU 维度。**同一货位同一 SKU 的连续任务无法关联，
  所以判断不了"是不是某个货位在反复缺货"。
- **90 / 12 分钟是给定的常数**，没有考虑多次缺货的叠加代价
  （波次延误、后续任务排队），真实损失可能被低估。
